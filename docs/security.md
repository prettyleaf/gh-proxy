# Модель угроз и что с ней сделано

Сервис приватный: им пользуетесь вы, а не интернет. Отсюда все решения ниже.

---

## 1. Сервис не должен себя обнаруживать

Открытый gh-proxy — это бесплатный трафик для всех, кто его нашёл, и ваш IP в
чужих логах. Поэтому:

* **Всё неавторизованное — `404`.** Не `401`, не `403`. Неверный токен,
  отсутствующий токен, не-GitHub URL, чужой префикс — один и тот же ответ, одно
  и то же тело. Различия в ответах были бы оракулом: по ним подбирается и факт
  существования сервиса, и корректность токена.
* **Нет `WWW-Authenticate`.** Браузер не покажет окно ввода пароля, сканер не
  увидит признака защищённого ресурса.
* **Нет главной страницы.** Оригинальный gh-proxy на старте скачивает HTML с
  `hunshcn.github.io` и отдаёт его на `/` вместе с favicon. Здесь этого нет
  вообще: корень — `404`.
* **`/healthz` живёт на отдельном порту** (`GHP_ADMIN_LISTEN`, по умолчанию
  `127.0.0.1:8900`) и никогда не публикуется наружу. Health-check под публичным
  префиксом был бы надёжным способом подтвердить, что сервис есть.
* **`X-Robots-Tag: noindex, nofollow, noarchive`** на всех ответах.
* **Секретный префикс** — первый слой. `/ivanghproxy/` угадать сложнее, чем `/`.

Проверка, что ничего не светится:

```bash
for p in / /ivanghproxy /ivanghproxy/ /ivanghproxy/wrong/https://github.com/cli/cli/tags; do
  printf '%s -> %s\n' "$p" "$(curl -s -o /dev/null -w '%{http_code}' "https://sub.example.com$p")"
done
# всё должно быть 404
```

## 2. Токен

Один общий секрет, `GHP_TOKEN`. Принимается в четырёх местах (см.
[clients.md](clients.md)), сравнивается через `crypto/subtle.ConstantTimeCompare`.

При старте сервис **отказывается запускаться**, если:

* токена нет и не выставлен явно `GHP_ALLOW_ANONYMOUS=1`;
* токен короче 16 символов;
* токен содержит `/`, `?`, `#` или пробел (он едет одним сегментом пути).

Генерация:

```bash
openssl rand -hex 24
```

### Где токен может утечь

Токен-в-пути удобен (работает с `git clone` без 401), но путь — не самое
приватное место. Что с этим сделано и что нужно сделать вам:

| Канал | Статус |
|---|---|
| `access_log` nginx | **ваша задача**: `access_log off` в блоке `location`, см. [nginx.md](nginx.md#5-access_log-off--иначе-токен-утекает-в-лог) |
| Логи приложения | закрыто: URL-ы не логируются, `GHP_LOG_TARGETS=0` по умолчанию |
| Заголовок `Referer` к GitHub | закрыто: `Referer` вырезается перед отправкой апстриму |
| `Authorization` к GitHub | закрыто: вырезается; наверх уходит только `GHP_UPSTREAM_TOKEN`, если он задан |
| `.git/config` после клона | **ваша задача**: см. предупреждение в [clients.md](clients.md#прозрачная-подмена-для-всех-репозиториев) |
| История shell | **ваша задача**: вариант с заголовком чище |
| TLS | путь шифруется целиком; но не ходите по HTTP |

### Ротация

Токен меняется правкой `.env` и рестартом — старые ссылки перестают работать
немедленно:

```bash
sed -i "s/^GHP_TOKEN=.*/GHP_TOKEN=$(openssl rand -hex 24)/" .env
docker compose up -d
```

Одновременно двух токенов не поддерживается — специально, чтобы не было соблазна
оставить старый «на время».

## 3. Это не открытый релей (SSRF)

Прокси ходит по URL, который прислал клиент. Если бы список хостов и путей не
проверялся, любой обладатель токена (или, при `GHP_ALLOW_ANONYMOUS=1`, любой
желающий) заставил бы сервер сходить на `http://169.254.169.254/`,
`http://127.0.0.1:8900/` или во внутреннюю сеть.

Границы:

* **Хост** сверяется с фиксированным списком: `github.com`, `www.github.com`,
  `raw.githubusercontent.com`, `raw.github.com`, `gist.github.com`,
  `gist.githubusercontent.com`. Сравнение точное, поэтому `github.com.evil.example`
  и `evilgithub.com` не проходят.
* **Путь** должен совпасть с одной из поддерживаемых форм (релиз, архив,
  blob/raw, git smart HTTP, tags, raw, gist). `github.com/cli/cli` — уже нет.
* **Схема** всегда принудительно `https`, даже если клиент прислал `http://`.
* **Редиректы** следуются только на `GET`/`HEAD`, не более `GHP_MAX_REDIRECTS`
  раз, и только на хосты из `GHP_REDIRECT_HOSTS` (по умолчанию — CDN-бэкенды
  GitHub). Редирект на любой другой хост → `502`, тело ответа его не называет.
* **Креденшелы, вписанные в целевой URL** (`https://user:pass@github.com/...`),
  отбрасываются.

Проверка:

```bash
for u in http://127.0.0.1:8900/healthz \
         http://169.254.169.254/latest/meta-data/ \
         https://github.com.example.org/a/b/releases/download/v1/f.zip \
         https://gitlab.com/a/b/releases/download/v1/f.zip; do
  printf '%s -> %s\n' "$u" "$(curl -s -o /dev/null -w '%{http_code}' "$BASE/$u")"
done
# всё должно быть 404
```

## 4. Что не уезжает на GitHub

Из исходящего запроса вырезаются: `Authorization`, `Cookie`, `X-Proxy-Token`,
`X-Real-IP`, `Forwarded`, все `X-Forwarded-*` и `Referer`.

`X-Forwarded-For` намеренно **не** проставляется (`SetXForwarded()` не
вызывается) — GitHub незачем знать адрес вашего клиента. С точки зрения GitHub
запрос приходит от сервера.

## 5. Что не приезжает от GitHub

Из ответа вырезаются `Set-Cookie`, `Content-Security-Policy`,
`Content-Security-Policy-Report-Only`, `Clear-Site-Data`.

`Set-Cookie` — важный: кука от `github.com`, прошедшая насквозь, установилась бы
**на ваш домен**, потому что для браузера ответ пришёл от `sub.example.com`.
`Clear-Site-Data` от GitHub мог бы вычистить данные вашего сайта.

## 6. Ограничение области

Даже с валидным токеном можно сузить, что вообще проксируется:

```bash
GHP_ALLOW_LIST=ivan              # только ваши репозитории
GHP_ALLOW_LIST=ivan,octocat/hello
GHP_DENY_LIST=*/secret-stuff
```

Сначала применяется allow-list (пустой = без ограничений), затем deny-list —
порядок как в оригинальном проекте. Всё отклонённое — `404`.

## 7. Приватные репозитории

`GHP_UPSTREAM_TOKEN` — это GitHub PAT, который прокси предъявляет **GitHub**, а
не клиентам. Он позволяет тянуть приватные репозитории и поднимает лимиты API.

Последствие: любой, у кого есть `GHP_TOKEN`, получает доступ ко всему, к чему
имеет доступ этот PAT. Поэтому:

* давайте PAT минимальные права (`contents: read` для нужных репозиториев);
* сузьте область через `GHP_ALLOW_LIST`;
* при кросс-хостовом редиректе `Authorization` снимается автоматически — PAT не
  уедет на CDN-бэкенд (который его и так отверг бы: подпись у него в query).

---

## 8. Изоляция процесса

Образ собирается на `scratch`: ни шелла, ни пакетного менеджера, ни утилит —
разворачиваться в скомпрометированном контейнере не с чем. В compose-файле:
`read_only: true`, `cap_drop: ALL`, `no-new-privileges`, uid 65534, публикация
порта только на `127.0.0.1`.

Зависимостей у сборки нет вообще — только стандартная библиотека Go, так что
supply chain сводится к самому Go.

## Чего этот сервис не делает

* **Не аутентифицирует пользователей по отдельности.** Токен один на всех, кому
  вы его дали. Кто именно скачал файл — по логам не восстановить (и это
  осознанный размен: логов почти нет).
* **Не ограничивает скорость и объём** сам по себе. Если это нужно —
  `limit_req` в nginx, см. [nginx.md](nginx.md#необязательное-усиление).
* **Не прячет трафик от GitHub.** GitHub видит запросы с IP вашего сервера.
* **Не защищает от вас самих:** `GHP_ALLOW_ANONYMOUS=1` превращает сервис в
  открытый релей. Включайте, только если доступ к listener'у ограничен чем-то
  ещё (VPN, IP allow-list, mTLS).
